## Evidence

1. **OCRmyPDF has low-risk preprocessing knobs worth testing before larger architecture changes.** Its documented recipes include `--rotate-pages` for cardinal-orientation correction, `--deskew` for crooked scans, `--remove-background` for noisy backgrounds, `--image-dpi` for images with missing/wrong DPI, language selection with `-l`, and sidecar text output. The docs warn that rotation aggressiveness can create false positives and that image-processing results should be reviewed, so these should be evaluated on local aggregate outcomes rather than enabled blindly. Source: https://ocrmypdf.readthedocs.io/en/latest/cookbook.html

2. **OCRmyPDF sidecar text is not a complete text extractor for mixed native/OCR PDFs.** The cookbook states sidecar output contains only OCR text found by OCRmyPDF; existing text is not included, and skipped pages are omitted. That supports keeping the current native extraction path for machine-readable PDFs and using OCRmyPDF as fallback/enrichment, not as the sole extractor. Source: https://ocrmypdf.readthedocs.io/en/latest/cookbook.html

3. **Tesseract configuration can change both quality and speed.** Tesseract CLI docs show defaults of English and page segmentation mode 3, support `--oem 1` for LSTM OCR, `-l LANG+LANG` for multiple languages, and note that language ordering can affect output and runtime. The same page documents HOCR output with block/paragraph/line/word metadata, which could support layout-aware post-processing or debugging without logging private text. Source: https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html

4. **Layout-aware extraction is now a plausible separate experiment, not just OCR text cleanup.** Docling describes PDF layout understanding, reading-order detection, table structure extraction, OCR support for scanned PDFs/images, and local/air-gapped execution. This makes it relevant for documents where raw OCR text is present but poorly ordered or where tables are important. Source: https://docling-project.github.io/docling/

5. **Table extraction requires corpus-specific tool selection and cannot be treated as generic text extraction.** Camelot’s comparison page emphasizes that different tools win on different inputs; it contrasts Camelot, Tabula, pdfplumber, PyMuPDF, model-based tools, and scanned-PDF capabilities. It specifically frames pdfplumber as useful when low-level layout primitives are needed, while Camelot offers table-level quality reports/confidence for typical reports. Source: https://camelot-py.readthedocs.io/en/stable/user/comparison.html

6. **pdfplumber remains useful for native PDFs and layout diagnostics but is not an OCR solution.** The pdfplumber project describes access to characters, lines, rectangles, curves, images, annotations, text extraction, table extraction, visual debugging, and layout-aware extraction, but states it works best on machine-generated PDFs and does not provide OCR or strong support for tables from OCRed documents. Source: https://github.com/jsvine/pdfplumber

## Recommendations

1. **First prioritize a privacy-preserving OCR parameter A/B harness for metadata-only reduction.** Test OCRmyPDF/Tesseract options against only files already classified as `indexed_metadata`, but report only aggregate counts, durations, and eval scores. This is justified because there are currently 10 metadata-only files and both OCR engines are available locally.

2. **Keep OCR as fallback/enrichment, not a replacement for native PDF extraction.** OCRmyPDF sidecar limitations mean the native path should remain authoritative when text already exists; OCR should target scanned/metadata-only cases or pages with insufficient extracted text.

3. **Add a layout/table extraction pilot only after the OCR parameter harness exists.** Docling/Camelot/pdfplumber add dependencies and complexity. The first milestone should be a read-only benchmark that compares aggregate conversion success, runtime, and retrieval impact on a small private fixture set or sanitized synthetic fixtures, not production indexing behavior.

4. **Expand evaluation before claiming quality gains.** The current aggregate eval has only 5 queries. Any OCR/layout change should be judged against the planned larger private eval set plus aggregate status counts; otherwise an apparent metadata-only reduction might not improve retrieval quality.
